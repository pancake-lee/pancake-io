photo-agent 功能基本跑通了：自然语言搜索照片、VLM 描述生成、LangGraph 路由、ChromaDB 向量检索、Text-to-SQL 结构化过滤。

作为一个个人项目，它已经能满足我的日常使用。

但做到后面，我开始感觉到一种比较明显的瓶颈：**不是"做不出来"，而是"不知道怎么做更好"。**

举几个让我卡住的场景：

- RAG 检索有时候返回的结果不太相关，但我不确定是 embedding 模型的问题，还是 chunking 策略的问题，还是检索流程本身的设计问题
- 分类器（决定走 SQL/RAG/Combined 哪个分支）偶尔误判，我想优化 prompt，但没有系统的方法论，只能靠反复试
- 看到别人用 CLIP 做多模态检索、用 ColBERT 做 token-level 匹配，我大概知道这些名词是什么意思，但判断不了它们是否适合我的场景
- 想给项目加一个正经的评估体系，但除了现在手写的 20 条黄金用例，不知道还有什么更好的方法

这些问题背后，缺的不是写代码的能力，而是对 AI 技术栈更系统的理解。我之前的学习方式是在项目中遇到什么学什么，这让我快速跑通了 MVP，但也让我对技术选型的判断力很有限。

所以我决定静下来，对照 [AI Engineer Roadmap](https://roadmap.sh/ai-engineer) 系统地过一遍 AI 的理论知识，把缺失的基础补上。

## AI Engineer vs ML Engineer

> 一位人工智能工程师(AI Engineer)利用预训练的模型以及现有的人工智能工具来提升用户体验。他们注重将人工智能技术应用于实际场景中，而无需从零开始构建模型。这与人工智能研究人员(AI Researchers)和机器学习工程师(ML Engineers)有所不同，后者更专注于创建新的模型或发展人工智能理论。

## AI vs. AGI

> AI = Artificial Intelligence 人工智能，通常被称为“狭义”或“弱式”人工智能，指的是那些旨在执行特定任务的系统。这些系统在预定义的范围内使用算法和统计模型来运作。它们不具备意识、直觉，也无法将某一领域的知识应用到其他领域。

比如：专门训练出用于玩超级马里奥的AI，但这个AI无法用于其他领域。

> AGI = Artificial General Intelligence 通用人工智能，指的是一种假设的智能形式，它能够理解、学习并应用知识来完成任何人类可以执行的智力任务。与狭义人工智能不同，通用人工智能系统将是自主的，并且能够独立解决跨领域的难题。

比如：当前各种聊天AI

## AI inference vs. training  AI 推理与训练的区别

> **Training** 训练是人工智能模型的第一个阶段。训练过程可能包括反复尝试的过程，或者向模型展示预期的输入和输出示例的过程，或者结合这两种方法。

> **Inference** 推理是人工智能训练之后的后续过程。模型训练得越精细、调整得越充分，其推理能力就会越好，尽管不能保证推理结果总是完美的。

## Fine-tuning

> 微调过程涉及使用已经预训练的大型语言模型，然后在其基础上再对其进行训练，但使用的是规模较小且针对特定任务的数据集。这样能够使得模型在特定的任务或领域中发挥更好的性能。不过，微调过程需要大量的资源，而且并不总是最有效的方法。**使用提示工程、增强型检索生成方法，或者采用规模较小但功能更专业的模型，有时可以在较少的计算资源和数据需求下获得相当甚至更好的效果。**

可以比喻成：**考前复习/补习**

## Prompt VS Context

提示词工程一般是指用户说的话，也会包含系统提示词，本质上只是预埋在应用里的预设的提示词。

而上下文工程是指模型获取到的一切，比起提示词工程，最明显的就是包含RAG结果。

我们在开发Agent时，一般是在做上下文工程，而用户输入时，更偏向于是提示词工程。

## Prompt Engineering

> 提示词工程是设计有效提示的艺术与科学，这些提示是给予大型语言模型的操作指令或输入。其目的是设计出能够引发语言模型产生预期响应的提示，从而引导模型生成准确、相关且富有创意的输出。这涉及到了解语言模型的能力与局限性，并尝试不同的提示结构、关键词以及上下文线索，以取得最佳效果。

但是不同模型，对提示词的要求是不是也不一样，

而且模型越来越厉害，现在对于描述得不够完整，结构化差的提示词，也能有更好的输出了。

况且，在agent开发中，我们还可以先让LLM帮我们做一次提示词优化，再输入到后面的环节。

但是基本概念还是可以过一过~

### System Prompting

> 系统提示设定了大型语言模型的整体上下文、目标以及操作指南。它明确了模型的角色、行为约束、输出格式要求以及安全保护措施。系统提示提供了基础参数，这些参数会影响后续所有的交互过程，从而确保人工智能的响应始终具有一致性、可控性且结构清晰。

学习最初期的时候，可以理解为岗位职责/工作指南/使用说明书等等，而一旦实践起来，很快就能掌握这个概念。无需过多刻意学习。以下是一些上下文编写的技巧，基本上都是阅读一遍就理解的内容，不展开细节。

- Role & Behavior 角色与行为
- Contextual prompting 情境提示
- Constraining Prompts 限制提示语
- Structured Outputs 结构化输出

### Zero-Shot Prompting（零样本提示）

是指 **不提供任何示例** ，直接向模型下达指令，要求其凭借预训练中学到的知识直接完成任务。可以比喻成**直接作答**。如：`请将中文‘香蕉’翻译成英文。`

### Few-Shot Prompting（少样本提示）

是指在提示词中 **提供少量（通常2-5个）完整的输入-输出示例** ，让模型在“推理时”通过这些示例理解任务模式，然后再处理新问题。可以比喻成**题目附带了答题示例/格式**。如：

```
示例1：评论‘屏幕清晰，电池耐用’ → 好评
示例2：评论‘塑料感重，价格偏高’ → 差评
示例3：评论‘拍照效果惊艳，系统流畅’ → 好评
现在请分类：‘充满电只能用半天，发热严重’
```

而超过5个示例之后，就算不上Few-Shot了，且不建议（实际上随着模型上下文限制逐渐增加，示例也可以更多，只是会被称为Many-Shot而已）。当实际样本超过5个，则应该引入**RAG**，检索出最相关的5个。

### ReAct

可能有点疑惑，但确实属于提示词工程，因为即使在各种Chat页面，也可以通过提示词来实现ReAct这个流程，但Act则工具执行的部分，需要人工代劳后输入到聊天中。

> ReAct（推理与行动）提示功能使得大语言模型能够通过结合推理与外部工具交互来解决复杂问题。其运作流程遵循思维-行动-观察的循环：首先分析问题，然后通过调用外部 API 执行相关操作，之后查看结果，并根据需要继续迭代直至解决问题。这一功能适用于研究场景、需要多步操作的任务，以及那些需要使用当前数据的任务。

### Chain-of-Thought Prompting

> 思维链是一种让人工智能代理能够大声思考的方法。在给出最终答案之前，代理会写下简短的笔记，记录下每一个操作步骤。这些笔记可以包含事实信息、子任务的名称，或者进行一些简单的计算。通过查看这些步骤，代理能够保持条理清晰，减少出错的可能性。阅读答案的人也可以检查逻辑是否正确，发现潜在的弱点。这些书面步骤可以被重新输入到代理中，以便其进行规划、反思或自我修正。由于思维链易于使用且能增强信任感，因此它成为当今基于语言的智能代理中最常见的设计方式之一。

这依然是提示词工程，并不是指代LLM的思考模式等其他技术。

```
请按以下步骤一步步推理，最后给出退款金额：
1.先确定使用天数区间，对应退款比例
2.计算基础退款金额 = 购买价 × 比例
3.检查是否有配件缺失，若有则再减30元
4.得出最终退款金额
用户评论：买了19天，充电线找不到了，手机本身没问题，想退货。购买价299元。
```

```
1. 使用天数：19天 → 超过15天，对应退50%
2. 基础退款金额 = 299 × 50% = 149.5元
3. 配件缺失：充电线找不到 → 减30元
4. 最终退款金额 = 149.5 - 30 = 119.5元
答：119.5元。”
```

### Input Format

指的是使用普通文本/Markdown/Json等不同格式输入时会导致输出的差异

[Does Prompt Formatting Have Any Impact on LLM Performance?](https://arxiv.org/html/2411.10541v1)

> 结论-摘抄/翻译
> 我们的研究表明，**提示的格式对基于 GPT 的模型性能有着显著的影响，没有一种格式能够普遍适用**。这一发现质疑了当前评估方法的合理性，因为这些方法往往忽略了提示的结构因素，从而可能误判模型的真实能力。我们建议在未来对大语言模型进行测试时采用多种不同的提示格式，以更准确地评估并提升模型的性能。
> 在可解释性方面，我们发现模型的大小会影响模型对提示变化的响应。例如，**与 GPT-3.5 相比，GPT-4 对提示变化的敏感度较低**，这表明较大的模型可能能够更一致地处理提示。这一发现促使我们进一步研究大语言模型的可解释性，以提升人工智能的适应性以及人类与人工智能之间的交互效果。

### Function Calling

虽然api上是独立的参数输入，但是本质上，也是一份接口文档拼接到最终给LLM的提示词中。

> 函数调用使得大型语言模型能够与外部工具和 API 进行交互。除了生成文本之外，还可以指令语言模型根据用户的输入来判断何时需要调用特定的函数，然后输出执行该函数所需的参数。这样，语言模型就可以执行超出其训练数据范围的任务，例如实时获取信息或自动化处理各种任务。

### Prompt Caching

> Prompt caching is a technique that stores the results of previous LLM prompts, allowing you to quickly retrieve and reuse them instead of re-running the prompt every time. This can significantly improve efficiency and reduce costs when dealing with frequently used or computationally expensive prompts.
> 快速缓存是一种存储之前生成的 LLM 提示结果的技术，这样你就可以快速获取这些结果并重复使用它们，而无需每次都重新生成提示。这对于处理经常使用或计算成本较高的提示时，可以显著提高效率并降低成本。

要注意这段描述的用词，并不是缓存LLM的生成结果，而是提示结果，实际上是节省Tokenization的消耗。

prompt -> tokenizer -> tokens

缓存这些处理好的tokens，一般包含附加到上下文中的各种文档，系统提示词等等。

而很可能/一般情况下，缓存机制会使用Prefix Matching，遇到和之前的缓存不一致的内容时，就开始放弃继续使用缓存，所以也说明了，我们管理上下文时，应该把变化的内容放到后面。

用词修正（但修正了反而不容易理解，在还没有深入学习Tokenization和Transformer之前，还不如先简单误解）

> 上述“并不是缓存LLM的生成结果，而是提示结果，实际上是节省Tokenization的消耗”表述不准确。Prompt Caching（提示缓存）缓存的是 将提示词（Prompt）转换为 Token ID 序列后的结果 ，节省的是**重复的 Tokenization 和 Prefill（预填充）阶段的 KV Cache 计算开销** ，而不仅仅是“Tokenization的消耗”。更准确地说，它缓存了 Transformer 处理 Prompt 前缀时生成的 KV Cache（键值缓存），使得后续相同前缀的请求可以跳过重复计算。
> 建议 ：修改为“ 缓存的是提示词经过 Tokenization 后，在模型 Prefill 阶段生成的 KV Cache（键值缓存），从而避免对相同前缀内容的重复计算，节省推理时间和算力。 ”

## Context Engineering

> 上下文工程指的是精心设计和组织提供给人工智能模型的信息的过程，从而让模型能够更有效地完成任务。可以把这看作是在人工智能开始工作之前，为它准备好所有所需的资源——包括正确的指令、示例、背景知识以及对话历史等。所有这些资源都被巧妙地整合在一起，从而让模型能够给出最佳的答案。与其只是提出问题然后期待最好的结果，不如打造一个完美的“信息环境”来引导人工智能走向成功。

### External Memory

> 在大型语言模型（LLM）的语境中，外部存储器指的是那些允许这些模型访问并利用存储在内部参数之外的信息的机制。这可能涉及在提示处理或生成过程中从数据库、知识图谱或其他外部源中提取相关数据，以丰富模型的知识储备，从而提高模型在特定任务上的性能。这有助于提升 LLM 处理复杂查询的能力，使其能够生成更精确且符合上下文需求的响应。

其实这更多是一种思路，而不是特指某个具体技术，比如CLAUDE.md也算是一种外部存储，主要是区别于agent内部的系统提示词，又区别于用户动态输入的用户提示。

### RAG and Dynamic Filters

> 基于检索增强的生成技术（RAG）通过从外部来源获取相关且最新的信息，从而提升了大型语言模型的能力。动态过滤机制能够选择性地筛选出适合特定查询和用户的上下文信息，使得大型语言模型能够获取最相关的内容。这样就能得到更加准确、有针对性且符合上下文需求的模型响应。

RAG用来做语义查询，而Dynamic Filters则是通过元数据做准确的筛选，两者是配合关系，不是简单的二选一。

### Context Compaction

> 上下文压缩是一种用于减少大型语言模型所接收的上下文长度的技术，同时不会丢失重要信息。这一过程旨在从上下文窗口中去除冗余、不相关或次要的信息，以便为模型容纳更多数据，或提高模型处理信息的效率与效果。上下文压缩可以采用摘要处理、过滤或重新排序上下文信息等方法来实现。

### Context Isolation

> 上下文隔离是指在处理大型语言模型时，将不同的任务或知识领域分离开来。可以把它想象成为每个任务分配一个独立的空间。这样一来，就不会有一个大型语言模型试图同时处理所有事务，而是可以使用多个较小的“代理”来分别处理特定任务，每个代理都只专注于特定的任务，并且只处理与其相关的数据。这样就能避免无关信息相互干扰，从而得到更准确、更可靠的结果。
