> 在开始阅读具体文章之前，先说明一下我对“Harness”这个词的理解：**Harness 是指 AI 工作中除了模型之外的所有其他工作**——包括提示词工程、上下文工程、Agent编排、工具调用、记忆管理、评估体系等等。它是一个非常宽泛的伞状概念，所以Anthropic文章里的三Agent系统是Harness的一种具体设计，OpenAI文章里的工作流管理也是Harness的一种具体设计，我自己的README.md驱动开发和pflow项目同样属于Harness Engineering的范畴。

## OpenAI 文章阅读笔记

这篇文章读下来，有好几个地方让我觉得“他洽”——很多我之前摸索出来的做法，在文章里得到了印证。

我在 CodeAgent 流行初期就开始用 README.md 来驱动开发：每次新对话第一句先让 Claude 读 README，然后执行开发任务。输出不满意时，我不会直接改代码，而是让 Claude 自己分析问题出在哪里，把分析结果写回 README.md，下一轮再继续。如此循环，直到输出让人满意的代码。整个过程里我刻意不碰代码本身。

回头看，这和 OpenAI 文章里说的“人类不直接写代码，而是通过设计环境和构建反馈循环来让 Agent 工作”是同一个思路。

pflow 这个项目也是从类似的观察出发的。我在和 AI 讨论问题时发现，AI 的工作流经常让人陷入注意力涣散的状态——该关注的时候没关注，不该打断的时候被打断。pflow 的设计初衷就是解决这个问题。这和文章里讲的“如何最大化利用我们唯一真正稀缺的资源：人类的时间和注意力”刚好对得上。

读到文章关于目录结构的部分，我确认了自己的目录规划和 OpenAI 的方向是一致的。虽然我的规划在时间上没有比这篇文章更早，但我做这些事情的时候并没有受到外界文章的影响，而是在开发过程中逐渐形成的。至少大方向是对的，很高兴这增加了我的自信。

下面记录一下我的目录结构和 OpenAI 方案的对比。

### 目录结构对比

**OpenAI 的目录结构：**

```sh
project/
├── AGENTS.md                     # AI入口，约100行，作为索引而非百科全书
├── ARCHITECTURE.md               # 顶层架构地图
├── docs/
│   ├── design-docs/              # 设计文档（含index.md、core-beliefs.md等）
│   ├── exec-plans/               # 可执行计划（active/、completed/、tech-debt-tracker.md）
│   ├── generated/                # 自动生成（如db-schema.md）
│   ├── product-specs/            # 产品规格（含index.md）
│   ├── references/               # 外部参考文档（llms.txt格式）
│   ├── DESIGN.md
│   ├── FRONTEND.md
│   ├── PLANS.md
│   ├── PRODUCT_SENSE.md
│   ├── QUALITY_SCORE.md
│   ├── RELIABILITY.md
│   └── SECURITY.md
```

**我的目录结构：**

```sh
project/
├── README.md                     # 人读：项目简介、术语、快速开始
├── CLAUDE.md                     # AI读：工作规则、代码风格、禁忌
├── todo.md                       # 当前周期任务清单
├── docs/
│   ├── archive/                  # 归档（rejected.md + 废弃文档）
│   ├── cycles/                   # 周期归档
│   ├── capture/                  # 可演示版本的截图
│   ├── product/                  # 产品文案、宣传材料
│   ├── design/                   # 设计思路/专题调研/实现方案
│   ├── changelog.md              # 版本历史
│   ├── backlog.md                # 全部需求池
│   ├── note.md                   # 活跃技术备忘
│   └── testing.md                # 测试策略、测试清单
```

### 共同点

两套方案共享几个核心思路。

首先是**渐进式披露**——不把全部内容塞进一个文件，而是让 AI 从一个入口文档开始，按需深入。OpenAI 用 AGENTS.md 做索引，我用 CLAUDE.md 做入口。本质是一样的：给 AI 一张地图，而不是一本字典。

其次是**结构化分层**——设计文档、产品规格、参考文档都按目录分类存放，而不是堆在根目录。

第三是承认“人读”和“AI 读”的差异。OpenAI 有 AGENTS.md，我有 CLAUDE.md，各自独立存在，服务不同的读者。

第四是知识必须沉淀到仓库中。OpenAI 强调“知识在 Google Docs、Slack、人脑里是无效的，必须编码进 repo”，我的目录结构也是把需求（backlog）、方案（design）、决策（archive/rejected）全部落在文件里。

第五是用工具来强制执行规则。OpenAI 用自定义 linter 和 CI 来验证知识库更新、架构边界和命名规范。我目前只有文档层面的约定，还没有走到“用代码检查文档”这一步，这是**需要推进**的。

### 差异点

| 维度         | OpenAI                                          | 我                                                             |
| :----------- | :---------------------------------------------- | :------------------------------------------------------------- |
| 入口文档定位 | AGENTS.md 约 100 行，作为“目录”指向各处         | CLAUDE.md 作为“工作规则”，包含具体执行指令（编译、测试、禁忌） |
| 计划管理     | exec-plans/，每个计划独立文件，含进度和决策日志 | todo.md（当前周期）+ backlog.md（全集）两条线分开管理          |
| 历史沉淀     | 没有明确的“周期归档”概念                        | cycles/ 按版本归档，capture/ 存截图，changelog/ 面向用户       |
| 归档意识     | 未显式管理“已拒绝/废弃”                         | archive/rejected.md 显式记录“为什么放弃”                       |
| 需求管理     | 没有显式的 backlog 结构                         | backlog.md 带优先级排序，维护全部需求池                        |
| 质量评估     | QUALITY_SCORE.md 给产品域和架构层打分           | 没有这个文件，但有 testing.md 描述测试策略                     |

### 从差异中看到什么

OpenAI 的目录结构是**面向“多 Agent 高频开发”设计的**。他们一天有 3.5 个 PR/人，100 万行代码在 5 个月内生成。在这样的吞吐量下，AGENTS.md 只做索引、计划独立文件、质量评分来跟踪趋势，都是为了让 Agent 在极短时间内获取足够上下文。

我的目录结构是**面向“人 + AI 共建的长期项目”设计的**。我在意周期的起止（cycles/），在意为什么放弃（archive/），在意需求池的完整视图（backlog/）。这更像是在帮助团队对齐，而不是在帮助高速流水线运转。

### 值得借鉴的地方

第一，**QUALITY_SCORE.md 这种形式**。用简单的评分跟踪每个模块的质量趋势，比“感觉哪里有问题”更客观，也能让 Agent 在决策时有参考依据。

第二，**计划粒度可以更细**。我目前是 todo.md + backlog.md 两条线，但 todo 一清空，上一周期的计划细节就只剩 cycles/ 里的归档了。如果计划在执行期间需要更精细的追踪，可以考虑给每个计划单独建文件。

第三，**把部分规则变成脚本**。目前目录规范还是纯文档约定，可以把部分规则做成脚本（比如用 Claude 执行 shell 命令去检查规则遵守情况），让 AI 自己验证，而不是等人工审查时才发现问题。

第四，**CLAUDE.md 需要控制行数**。OpenAI 把 AGENTS.md 控制在约 100 行，这是一种有意识的“克制”。我的 CLAUDE.md 可能会越写越长，需要持续注意这件事——把细节不断移到具体文档里，而不是堆在入口文件。

关于 lint 的使用，文章提到让 lint 的错误信息直接包含修改方案，这样 Agent 拿到错误就能自己修。另一个要点是明确哪些有限制、哪些没有限制，后者能给 AI 足够的自主空间，而不是把所有自由度都收窄。

关于 PR 合并策略，文章提到在高吞吐量环境下“纠错成本低，等待成本高”。当 CodeAgent 并行开发不同功能时，PR 不应该因为失败而阻塞其他提交。让合并失败的等待时间减少，因为修 Bug 的成本比等人审批低得多。

> 这里我联想到 pflow 的应用场景：提供更友好的注意力引导，让用户顺理成章地关注到“等待”，而不是强制提醒，也不是因被动发现而带来的延迟。
> 这只是一个小灵感，并不足以打断本笔记的核心思路。

文章还归纳了 Agent 应该输出哪些内容。这应该和目录结构的设计一起考虑，甚至可以为仓库制作一个开发流程图，把文档组织、代码结构、Agent 工作流串联起来。

## 引发的思考 - 思路转变：从解决问题到打通工作流

这是一个思路的转变，实际上也就是10来分钟的事情，上面我的笔记还是在“如何优化我的这些Harness建设”的考虑上。

以及考虑这些内容如何能提高我Photo-Agent的产品功能效果。但突然我意识到，我似乎不需要纠结这里的“技术方案”，至少不需要我直接输出方案。

过去我在面对产品效果不佳的时候，习惯性的反应是：我自己去想技术方案——应该用什么方法、调整什么参数、修改什么逻辑。

这个反应模式在传统开发中是合理的，因为代码是我写的，问题只能由我来修。

但现在情况变了。代码是 AI 写的，我不应该继续把“如何提升效果”当作一个技术问题来自己解决。

我的职责边界变了，我需要做的事情是：

1. 定义什么是“好效果”，说清楚我期望达到什么标准
2. 把当前效果和期望效果都告诉 AI
3. 让 AI 自己去想方案、去实现
4. 观察 AI 的工作流在哪里卡住
5. 打通这些工作流的障碍，补全文档、调整规则、优化上下文传递

在这个过程中，技术方案的制定、实现、验证，全部交给 AI。而在初期，我可以先参与每个环节的审核，只是为了先确保AI的方向不会走得太偏，但千万不能直接动手。

一旦某个环节达到了一个不错的效果后，应该让工作流先流转起来，因为缺陷和效果都将合理地出现在工作流中，并且通过工作流的循环，最终修复缺陷/提升效果。

如此，我的角色从“解决问题的人”变成“让解决问题的人（AI）能够顺利工作的人”。

这不是放弃对效果的关注，而是换一种方式去达成效果。过去我纠结的是“产品功能还不够好”，现在应该想的是“AI 的工作流还不够顺畅”。把后者打通了，前者自然会改善。

这个转变对应到 OpenAI 文章里的表述，就是“人类掌舵，智能体执行”——掌舵的意思是判断方向，而不是亲自划船。

## Anthropic

[www.anthropic.com/engineering/harness-design-long-running-apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)

文章一开始讲述了他们发现三代理系统的过程，这些经验我相信每次看都会有新的感悟，就不抄写了，遇到问题时阅读一下，也许会有新的理解和灵感。

记一下三代理的笔记（机翻，仅笔记，真的要参考着去落地时，一定要看原文）：

> 规划器：我们之前的长期运行的操作程序需要用户提前提供详细的规格说明。我想自动化这一步骤，因此创建了一个规划器代理，它可以将简单的 1-4 句提示扩展成完整的产品规格。我提示它要大胆设定范围，并专注于产品上下文和高级技术设计，而不是详细的技术实现。这种强调是由于担心如果规划器在前期尝试指定详细的技术细节并出错，规格中的错误会级联到下游实现中。看起来限制代理生成的交付物，让他们在工作中自行找出路径要明智得多。我还要求规划器在产品规格中寻找将 AI 功能编织进去的机会。（见附录中的示例。）

> 生成器：早期套件中的一次一个功能的方法对于范围管理效果很好。我在这里应用了类似的模型，指示生成器以迭代的方式工作，一次从规范中获取一个功能。每个迭代都使用 React、Vite、FastAPI 和 SQLite（后来改为 PostgreSQL）堆栈来实现应用程序，并指示生成器在每个迭代结束时自我评估其工作，然后再交给 QA。它还使用了 git 进行版本控制。

> 评估器：早期 harness 的应用在外观上往往看起来很令人印象深刻，但在实际使用时仍然存在实际错误。为了捕捉这些错误，评估器使用 Playwright MCP 按照用户的方式点击运行中的应用程序，测试 UI 功能、API 端点和数据库状态。然后，它根据发现的错误和一套基于前端实验的标准对每个冲刺进行评分，这里将其调整为涵盖产品深度、功能、视觉设计和代码质量。每个标准都有一个硬性阈值，如果任何一个低于该阈值，冲刺就会失败，并且生成器会收到关于出错原因的详细反馈。

其实这3个Agent的分工也就是我们常见的开发流程的分工，产品/开发/测试。当然不同组织发展出了更多节点甚至更多形式，但最基础的就是这3个环节了。我们接下来看写作过程。

> 在每次冲刺之前，生成器和评估器会协商一个冲刺合同：在编写任何代码之前，就那部分工作“完成”的标准达成一致。这存在的原因是产品规范有意设定得比较高级，我希望有一个步骤来弥合用户故事和可测试实现之间的差距。生成器提出了它将构建的内容以及如何验证成功，评估器审查了那个提案以确保生成器正在构建正确的东西。两者迭代直到达成一致。

这相当于我们的开发评审吧，开发人员输出开发方案，而测试人员输出测试用例，双方需要会议评审是否有理解差异，最终把目标对齐一致。进一步的自然就是根据“对齐一致的目标”，回顾一下产品设计，看是否完成了所有需求，是否有风险，成本是否太大等等。

> 通信通过文件处理：一个代理会写入一个文件，另一个代理会读取它并响应，要么在那个文件中，要么用一个新的文件，之前的代理会依次读取。生成器在将工作交给 QA 之前，会根据商定的合同进行构建。这保持了工作忠实于规范，同时避免了过早地过度指定实现。

这个通讯方式和前面OpenAI的文章是能接起来的，人和Agent，Agent之间的沟通，都需要持久化地落到文件上，并且建立其索引，达到渐进式披露的效果。

后面大篇幅的内容，都是讲述如何提高生成器和评估器的工作效果，也提到模型升级会引发Harness如何变化/调整。

这篇文章更多是引发/激发思考的那种形式，非提供可复用的结构化知识，实际上没有太多可以形成”笔记“的内容。

更适合当方向不明时，回来阅读一下，也许会有不同的发现，所以”笔记“也到此为止了。

## 引发的思考 - 关于“一句话驱动”的思考

Anthropic文章讲述了这个“3Agent系统”的使用效果，着重表达了基于一句或者有限的几句描述，这个系统能输出多么令人惊喜的输出，这个输出比单个Agent的使用优秀得多。

这里我需要停下来，仔细审视“一句话驱动”这种输入方式——因为这和我的日常工作方式有本质差异，我需要把这个差异想清楚，才不至于误判这个Harness设计对我是否有参考价值。

下面是我从这个角度出发的思考，并**不代表对两篇文章的全面分析**，但也确实是我阅读这两篇文章时的思考，记录在这里并**不代表**这就是“全面分析这两篇文章”而得到的感想，仅仅是从一个小点引发的思考而已。

### 我的第一个反应：这不符合开发人员的工作习惯

开发人员不是靠“一句话”工作的。我作为一个开发人员，看到需求之后，第一反应不是“行，开始做”，而是会想：

- “这个功能大概涉及哪几个模块？”
- “数据库表结构要怎么设计？”
- “我之前写过类似的东西吗？有什么坑？”
- “这个方案可行吗？有没有更好的方式？”

这些思考是多年工程训练形成的习惯，甚至很多时候是无意识的。所以当我看到一个系统宣传“一句话就能做出完整应用”时，我本能地觉得：“这不符合我怎么工作的啊。”

但这不是在否定Anthropic的Harness设计，而是说明：**这个Harness设计的目标场景，可能和我平时工作的场景不一样**。我需要先搞清楚它适合什么场景，再判断它能给我带来什么启发。

再次明确，这不是在否定Anthropic的文章，事实上，该文章讲述的如何提高输出质量的经验非常有指导意义。

### 进一步想：“一句话”模式到底在证明什么？

Anthropic用“一句话”作为输入，不是为了告诉开发者“你们以后只用一句话就行了”。它更像是一次**能力演示**——用极简的输入来凸显Harness本身的编排能力和模型的自主性。

它的逻辑是：“如果一句话都能驱动出这样的结果，那么更详细的输入应该能驱动出更好的结果。”这是一个合理的演示策略，但需要警惕的是——不应该把它理解为“这就是开发人员的工作方式”。

开发人员当然可以提供更详细的输入——方案设计、技术选型、边界条件、非功能性需求——**这本来就是我们在做的事情**。而Harness的价值在于，它能把开发人员提供的这些“更详细的输入”转换成更稳定、更高质量的输出。

所以“一句话驱动”是演示用的，我需要提醒自己：不要把它当作“最佳实践”来理解。

### 那“一句话”模式究竟适合什么场景？

经过上面的思考，我意识到“一句话驱动”有它自己的适用场景，但不是全部场景。它更接近一种“创造性工具”：

- **创意探索期**：当你自己也没想清楚“这个东西做出来可能是什么样”，用“一句话”启动Agent，让它给你做几个不同方向的Demo，然后你再判断方向。这比用传统方式去构思、画图、写文档快得多。
- **概念验证**：老板或客户问“这个想法你觉得能做吗？”，你可以在几小时内让Agent产出可交互的原型，用来对齐预期、降低沟通成本。这时原型的作用是“沟通工具”，而不是“交付物”。
- **Harness开发者的自我检验**：开发Harness的人，用“一句话”跑一遍，能快速检验编排是否稳定、Agent之间的协作是否顺畅。这是一种测试方法，而不是一种工作方法论。

**但这些场景结束后，真正的开发工作还是要回到更细致的共建模式。** 一句话可以点燃火种，但不能代替燃烧本身。

### 另一种模式：我在做的“共建式Harness”

我自己的Harness设计思路是另一个方向——**渐进式共建**。

可能这只是 Human In The Loop 的 Harness Engineering ，共建是我自己起的名字，但对于我自己来说很贴切。

回顾我之前的开发实践（README.md驱动开发、pflow管理注意力等），我一直在做的事情是：**让AI在已有的知识和产物基础上工作，而不是每次都从零开始。**

这种“共建”模式有几个特点：

- **项目是有历史的**：代码、文档、讨论记录、决策理由都会累积。我从来不在空白画布上工作，而是在一个不断生长的语境中工作。
- **需求本身会演进**：我在开发过程中，需求会被不断澄清、细化、调整。这不是因为“没想清楚”，而是因为**开发过程本身就是需求逐步清晰的过程**。
- **我的思考有价值**：方案设计、技术选型、风险评估、代码审查——这些都是开发人员的核心价值。如果把这些都交给AI，我就变成了“需求转述员”，而不是工程师。
- **积累本身就是Harness的一部分**：README.md也好，pflow也好，本质上都是在把“项目上下文”做成可持久化、可渐进式披露的结构。这就是Harness Engineering的一部分。

所以，“共建”不是“不用Harness”，而是**一种更注重长期演进的Harness设计风格**。

### 回到Anthropic那篇文章：两种Harness设计风格并存

现在我可以更清晰地定位Anthropic的Harness设计和我的Harness设计之间的关系了：

|                  | Anthropic 风格               | 我的风格（共建）               |
| :--------------- | :--------------------------- | :----------------------------- |
| **输入特征**     | 极简输入，Agent自主展开      | 持续输入，渐进式积累           |
| **适用阶段**     | 创意探索、原型验证、概念验证 | 长期项目、正式开发、持续演进   |
| **人与AI的关系** | AI先行展开，人做评价和校正   | 人与AI共同决策，共同成长       |
| **产物特征**     | 一次性的“惊喜”输出           | 可积累的知识资产、可维护的系统 |

**它们都是Harness Engineering的实现方式，服务于不同的项目阶段和不同的组织需求。**

Anthropic展示的Harness设计，解决的是“从0到1”的效率问题——用极少的输入撬动Agent的创造力，快速产出可体验的原型。而我在做的Harness设计，解决的是“从1到100”的稳定性和积累性问题——在项目演进过程中，让知识不断沉淀，让AI在越来越丰富的上下文中工作。

两种设计各有价值，不是替代关系，也不是谁更高级。

### 为什么这个区分很重要？

如果不做这个区分，我可能会陷入两种误区：

1. 看到一个“一句话做全栈”的演示，就开始怀疑自己的工作方式是不是有问题——“别人一句话就能做出东西，我为什么还要花这么多时间写文档、做设计？”（这就是我之前笔记里短暂出现的自我怀疑）
2. 或者反过来，完全否定Anthropic那套Harness设计的价值——“那不适用于我真正的项目，只是炫技。”

两种极端都是片面的。正确的位置是：**我知道两种Harness设计风格的存在，我知道它们分别适用于什么场景，然后根据手头任务的性质，选择或组合使用它们。**

### 技术人角度再审视：Harness Engineering的组织定位

文章后面的实验里，Anthropic用“一句话需求”驱动三Agent系统输出了完整应用，效果确实惊艳。从纯粹的技术角度看，这套Harness设计是有效的。

但把视角拉回到组织层面，我产生了一个新问题：**这种Harness设计，在实际团队中到底谁在用？谁会是它的直接操作者？**

负责Harness Engineering的同事，在Harness还没构建好之前，其实是靠自己的能力在做开发——他们会自己写代码、做方案、解决技术难点。等到Harness足够可靠了，它才能真正投入使用。**所以Harness Engineering首先优化的是开发人员自己的工作流，而不是让“非技术人员自助生产”。**

这反过来又影响了我对两种Harness设计风格的判断：

- Anthropic的Harness设计（极简输入、自主展开）——适合需求方直接使用，但前提是需求方愿意接受“AI先输出，我再评价”的工作模式，这需要一定的信任感和适应成本。
- 共建式Harness设计（渐进式积累、人机协作）——更适合开发人员自己使用，因为它保留了开发人员在各个环节的决策权和参与感。

两者在组织中的位置不同，使用者的角色也不同。这让我意识到，不应该轻易放弃“共建”的方式——因为它更贴合我现在作为“开发人员”的工作习惯和职责范围。

### 最终结论 - 灵活选择或融合两套模式

我认同Anthropic那篇文章的技术成果，但不认为“一句话驱动”是开发工作的终极形态。**“一句话”模式是Harness Engineering的一种有效演示形式和特定场景下的工具，而“共建”模式是另一种同样有效的、更注重长期演进的Harness Engineering实践。**

两者都属于Harness Engineering的范畴，前者偏向“从0到1”，后者偏向“从1到100”。一个完整的Harness Engineering实践，应该能够根据项目阶段和任务性质，在这两种风格之间灵活切换，而不是把自己绑定在某一种方式上。
