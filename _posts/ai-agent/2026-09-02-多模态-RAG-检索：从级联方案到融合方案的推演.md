在构建包含图片内容的多模态 RAG 系统时，图片如何参与检索流程，有两种典型的技术路径。这篇记录我对这两种方案的理解和对比，以及最后落到的一个折中架构。背景是我在做的 photo agent，需要把本地照片库变成可检索的知识源。

## 方案A：级联方案（图片 → 文本 → 向量）

这是我最初采用的流程，核心思路是把图片「翻译」成文字，然后复用整套文本处理体系。

**基本流程：**

1. **图片识别**：用图像识别模型（如 BLIP、GPT-4V、OCR 等）将图片内容转化为一段自然语言文本描述，例如「一只金色的金毛犬在夕阳下的海滩上奔跑」。
2. **文本向量化**：将上述文本描述通过文本 Embedding 模型（如 text-embedding-ada-002）转换为稠密向量。
3. **向量存储与检索**：向量存入数据库。用户输入文字查询时，同样将查询语句向量化，进行相似度检索。
4. **结果映射**：检索到的向量对应的是图片的文本描述，再通过该描述映射回原始图片，返回给用户。

## 方案B：多模态联合方案（图片 → 直接向量）

这是我考虑升级的方向，核心是使用能同时理解图片和文字的多模态模型，将两者编码到同一个向量空间。

**基本流程：**

1. **直接向量化**：用多模态 Embedding 模型（如 CLIP、ImageBind）直接对图片像素进行编码，生成语义向量。
2. **向量存储**：将该向量存入数据库。文字查询也由同一个多模态模型的文本编码器转化为向量。
3. **跨模态检索**：图文向量位于同一空间，可以直接计算相似度。用户输入文字可以直接检索到语义相关的图片。

## 一个让我犹豫的问题

在考虑是否要「抛弃」方案A、全面转向方案B时，我遇到了一个比较实际的困惑。

方案B虽然可能检索效果更好，但它把图片的文本描述这个中间产物丢弃了。这带来两个问题：

1. **调试变得困难**：方案A中，我可以随时检查生成的文本描述，验证「图片→文字」这一步是否准确。如果检索结果出错，可以定位是识别的问题还是检索的问题。方案B则像一个黑盒：它直接返回图片，我很难解释它为什么选中了这些图片。
2. **人工审核失去了抓手**：方案A允许我在入库前对文本描述进行审核、修正或补充标签，相当于对图片建立了一份人工可读的索引。方案B则直接将图片转化为难以解读的高维向量。

后来我意识到，这个困惑可能源于我作为系统设计者的一种本能，希望在每个环节都有可观测、可验证的中间结果。这不一定是个必须克服的障碍，而可能是一个需要被纳入架构设计的真实需求。

## 两种方案的对比

| 对比维度           | 方案A：级联方案                                       | 方案B：多模态联合方案                              |
| :----------------- | :---------------------------------------------------- | :------------------------------------------------- |
| **核心思路**       | 将图片问题转化为文本问题                              | 在向量空间统一理解图文                             |
| **信息保留程度**   | 较低。图片→文本环节会丢失颜色、纹理、构图等视觉细节。 | 较高。直接编码像素级和语义级特征。                 |
| **语义检索能力**   | 一般。只能检索到文本描述中明确提到的概念。            | 较好。能捕获更抽象的视觉语义（如「动态感」「氛围」）。 |
| **跨模态检索**     | 不支持。本质仍是文本搜文本。                          | 支持。可以实现文搜图、图搜文、图搜图。             |
| **可解释性**       | 较强。有可读的中间文本，便于调试和审核。              | 较弱。系统缺乏可解释的检索依据。                   |
| **工程复杂度**     | 较高。需维护图像识别和文本Embedding两套模型。         | 较低。只需维护一个多模态模型。                     |
| **人类认知友好度** | 较高。文本描述帮助人快速理解图片内容。                | 较低。需自行通过视觉判断验证结果。                 |

## 一个折中的思路：融合方案

对比之后，我感觉方案A和方案B各有利弊，不一定非要二选一。一个比较自然的想法是：能不能把两者结合起来？

### 融合方案的基本架构

**离线入库阶段（对每张图片并行执行）：**

1. 用多模态模型（如 CLIP）生成图片的语义向量 `v_img`，存入向量数据库。
2. 用图像描述模型（如 BLIP、GPT-4V）生成图片的自然语言描述 `T_desc`。
3. 用文本 Embedding 模型将 `T_desc` 转换为文本向量 `v_txt`，存入数据库。
4. 将图片ID、图片文件、文本描述 `T_desc`、两个向量 `v_img` 和 `v_txt` 关联为同一条记录。

**在线检索阶段：**

1. 当用户输入查询 Q 时，同时发起两路检索：
   - **语义路径**：用多模态模型的文本编码器编码 Q，对 `v_img` 进行检索，得到视觉相关的结果。
   - **文本路径**：用文本 Embedding 模型编码 Q，对 `v_txt` 进行检索，得到文本描述相关的结果。
2. 将两路候选结果合并，做简单的融合排序。
3. 返回图片列表，并在每张图片下方展示其预先生成的文本描述 `T_desc`。

### 这个方案解决了什么问题

- 用多模态检索保证了视觉层面的召回质量。
- 保留了文本描述作为可读的审计线索，便于调试和人工审核。
- 两路检索互为补充，单一模型的偏差可能被另一路弥补。
- 入库前的文本描述审核流程可以继续保留。

代价是存储空间和计算资源的增加，以及系统复杂度的提升。这是一个需要根据实际业务场景去权衡的选择。

## 结语

从最初的级联方案，到考虑升级为多模态联合方案，再到最终形成一个融合架构，这个过程本身解决了我对「可解释性」和「检索效果」之间如何取舍的困惑：两者不一定是单选题，中间产物（文本描述）值得作为架构里的一等公民保留下来。
