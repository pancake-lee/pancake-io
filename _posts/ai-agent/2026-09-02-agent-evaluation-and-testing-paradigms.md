之前在 RoadMap 系列第四篇里记过 Agent 评估的实践面：该追哪些指标、单测和集成测怎么落地、HITL 怎么做。这篇补理论体系：把传统软件测试的术语完整地映射到 Agent 评估上，再看看 AI 带来的新范式。整理自一段学习讨论，不少地方是我的个人理解，不一定是严谨的，但是有利于用传统的知识概念来快速理解新的 AI 概念。

## 一、AI 与工作方法：WBS 范式依然有效

AI 的出现并未颠覆传统的工作方法，无论是 **WBS（工作分解结构）**、**编程思维**，还是**将复杂问题拆解为简单问题的组合**这一核心思路，依然行之有效。

AI 只是为「任务拆解后的某个具体步骤」提供了一种新的实现方式。在过去，这个步骤可能是由人工完成的，也可能是借助现成软件或编写固定代码来执行的。而现在，那些原本难以用确定逻辑的代码来完成的步骤，可以交由 AI 来处理。

### 两种反驳与回应

- 「很多任务连拆解都不需要了，AI 能直接完成。」
- 「WBS 本身也是一个步骤，这个步骤同样可以用 AI 来完成。」

这些观点并不矛盾，反而引出了更实际的考量：一个步骤究竟该由人工、固定代码来执行，还是 AI 来完成，关键要看「性价比」，也就是成本与效果的平衡。如果某个步骤用 AI 成本偏高、效果还不够稳定，那么让人类参与进来，反而是更理性的选择。

### 创造力不可替代（个人见解）

假设有一天 AI 足够强大，每一个步骤都能完美替代人工，那是不是就万事大吉、不再需要人的参与了？

我目前的答案是否定的。AI 本质上仍然是一个程序，哪怕我们人为地加入随机数，它终究是硬件上数字信号的有限组合，只不过这个「有限」的边界极其宽广。而人类才拥有真正意义上的**创造力**。有些所谓的「灵感」，并不是像程序那样遵循某个固定的方法或逻辑就能产生的。

所以，AI 可以成为我们无比强大的执行伙伴，但那个负责「提出好问题、赋予任务意义、产生真正灵感」的角色，依然只能属于人。

## 二、Agent 评估闭环

### 核心流程

**输出 → 评审 → 修改 → 再输出**

评审就是用来定制、优化 Agent 的一个重要方法。这个环节可以有多种方法来落实：

1. **人工评估**：人给出反馈，加入到上下文里，让 LLM 再次输出
2. **代码评估**：编写代码，得出一些明确的量化指标（比如准确率、耗时）
3. **LLM 评估**：同样输入给 LLM，让它来评估当前输出，并给出改进建议

### 专业术语

- **Evaluation（评估）**：最通用的术语
- **Critique（评审/批判）**：特指让 LLM 或人对输出进行「挑剔性」分析
- **Reflection（反思）**：Agent 自己对输出进行审视并改进
- **LLM-as-a-Judge**：用大模型来评估另一个模型或自身的输出
- **Feedback Loop（反馈回路）**：强调整个循环过程

## 三、与敏捷开发的类比

Agent 的优化流程与敏捷开发（Scrum）有相似之处：

| Agent 侧                     | 敏捷开发侧                           |
| ---------------------------- | ------------------------------------ |
| 设定 Agent 的目标和性格/规则 | **Sprint Planning（迭代计划）**      |
| Agent 执行任务、输出结果     | **Sprint Execution（迭代开发）**     |
| 人工/代码/LLM 评估           | **Sprint Review（冲刺评审）**        |
| 总结记忆用户习惯，持续优化   | **Sprint Retrospective（迭代回顾）** |
| 下一轮「输出-评审-修改」     | 下一个 Sprint                        |

> 注意：这只是类比，Scrum 有固定的角色、仪式和时间盒，Agent 优化更松散。

## 四、测试术语与 Agent 评估的映射

这是这篇笔记里我觉得最有价值的部分：把传统测试的四个维度整体搬过来，每个维度都能在 Agent 评估里找到对应物。

### 维度一：按测试阶段（由小到大）

| 测试级别       | 核心关注         | Agent 评估对应                   |
| -------------- | ---------------- | -------------------------------- |
| **单元测试**   | 最小代码单元     | 单个工具调用、单个 Prompt 响应   |
| **集成测试**   | 模块间接口协作   | 多步推理链路、记忆与决策模块配合 |
| **系统测试**   | 完整系统整体表现 | 完整环境中从接收到输出的闭环     |
| **端到端测试** | 模拟真实用户操作 | 完整用户场景，从开始到目标达成   |
| **验收测试**   | 用户视角确认交付 | 真实用户评估是否「好用」         |

### 维度二：按测试方法（代码可见性）

| 测试方法     | 特点                           | Agent 评估对应                   |
| ------------ | ------------------------------ | -------------------------------- |
| **白盒测试** | 了解内部逻辑，基于代码结构设计 | 检查推理链路、决策分支覆盖       |
| **黑盒测试** | 只关注输入输出                 | 只给输入，不看思考过程，判断输出 |
| **灰盒测试** | 有限内部知识，从外部接口测试   | 查看「思考过程」但不深入模型参数 |

> AI 系统具有**概率性、黑盒性、非确定性**，传统「断言实际==预期」模式天然失效，测试需从**功能验证**转向**质量评估**。

### 维度三：按测试目的（质量属性）

| 测试类型       | 核心关注               | Agent 评估对应                  |
| -------------- | ---------------------- | ------------------------------- |
| **功能测试**   | 是否实现规定功能       | 是否完成用户任务                |
| **性能测试**   | 响应时间、吞吐量       | 响应速度、推理步数、Token 消耗  |
| **压力测试**   | 超负荷条件下的表现     | 大量并发时是否稳定              |
| **安全测试**   | 漏洞发现               | Prompt 注入、越权、敏感信息泄露 |
| **兼容性测试** | 不同环境下的可用性     | 不同平台/上下文表现是否一致     |
| **回归测试**   | 新修改是否破坏已有功能 | 更新后旧用例是否仍通过          |
| **冒烟测试**   | 最基本的「能不能跑」   | 快速验证核心链路是否畅通        |
| **可靠性测试** | 长时间运行稳定性       | 运行 1000 次的失败率            |

### 维度四：测试策略

- **测试左移**（Shift Left）：在需求/设计阶段就制定评估标准
- **测试右移**（Shift Right）：上线后持续收集用户反馈作为优化依据

### 总映射

| Agent 评估方式 | 对应的测试术语                         | 所属维度               |
| -------------- | -------------------------------------- | ---------------------- |
| 人工评估       | 手工测试 / 验收测试 / 探索性测试       | 执行方式 / 阶段 / 方法 |
| 代码评估       | 自动化测试 / 单元测试 / 集成测试       | 执行方式 / 阶段        |
| LLM 评估       | LLM-as-a-Judge / 灰盒测试 / 自动化评估 | 方法 / Agent 专项      |

## 五、AI 测试的新范式

### LLM-as-a-Judge

用一个 LLM 充当「裁判」，依据设定的评分标准，对被测 Agent 的输出进行打分并给出改进建议。

### Agent-as-a-Judge

用一个专门的「评审 Agent」来评估另一个 Agent 的整个任务执行过程。

### 根本差异

传统软件测试：**输入确定 → 输出确定 → 断言成立**

AI 系统测试：**概率性输出 → 质量评估 → 判断好坏**

测试工程师的角色，从「断言编写者」转变为「评测体系设计者」。

## 六、记忆口诀

**一横一纵一深度，加上策略和专项**

- **横向**（按阶段）：单元 → 集成 → 系统 → 端到端 → 验收
- **纵向**（按方法）：白盒 → 灰盒 → 黑盒
- **深度**（按质量）：功能 → 性能 → 安全 → 兼容 → 回归 → 冒烟
- **策略**：测试左移 / 测试右移
- **专项**：LLM-as-a-Judge、Agent-as-a-Judge
